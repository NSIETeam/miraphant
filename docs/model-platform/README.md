## 3. 产品决策

- 客户余额、充值、用量与预算统一用“积分”。默认 **人民币 1 元购买 100 积分**。
- “访问密钥”替代界面中的 API Token 名称，避免与模型 token 混淆。
- 模型协议内的 token、`usage` 字段保持兼容，管理账单保留底层计量依据。
- 不存在跨模型通用的“1 token＝若干积分”；根据模型、输入、输出和缓存分别计价。
- 首期单次充值，不做自动续费。充值档位建议 10／50／100／500 元，对应 1000／5000／10000／50000 积分，首期无充值赠送。
- 首期支持文本模型计费。图片、语音、视频与外部工具费用须独立定义单位和价格，未配置时不得展示可购买承诺。
- 客户能查看“这些积分大约能做什么”，同时看到模型档位、估算假设和实际扣费记录。

## 5. 支付与积分账务设计

在受控网关源码中增加支付模块，复用现有用户身份，订单、积分账本和余额更新使用同一事务边界。若日后拆分支付服务，也必须通过具备幂等键的内部入账接口，禁止直接写网关数据库或盲目重试旧充值接口。

v0.6.10 的 `AdminTopUp` 直接增加额度，再记录日志，没有支付订单幂等键；现有 `/api/topup` 不能直接承担可重试的支付入账。

最小数据实体：

- `payment_orders`：商户订单号、用户 ID、支付渠道、应付分、币种、购买积分、套餐版本、状态、过期时间。
- `payment_events`：通知唯一键、渠道交易号、验证结果、处理状态；仅存脱敏摘要与必要证据。
- `point_ledger`：唯一业务键、用户、充值／赠送／消耗／退款／调整、积分变化、关联订单或请求、价格版本。
- `point_holds`：模型请求或退款的积分冻结、释放及结算。
- `refunds`：退款单号、原支付单、退款金额、冻结积分、审核人与渠道状态。
- `price_versions`：生效时间、模型映射、积分费率、成本与汇率快照、发布人。
- `admin_audit`：价格变更、补账、退款、权限和支付开关操作及原因。

订单状态：`created → pending → paid → credited`；支付前可关闭或失败。退款独立跟踪。支付成功与积分到账分开表示，不能将已付款但待入账显示为付款失败。

到账规则：

1. 从登录会话确定用户，服务端计算金额和积分；客户端提交的用户 ID、金额、兑换比例不能作为可信依据。
2. 校验支付通知签名、商户／AppID、订单号、币种、应付金额和成功状态。
3. 用唯一订单号、渠道交易号及账本业务键阻止重复入账。在一个事务中写入到账记录、更新余额并标记 `credited`。
4. 通知可靠落库后返回确认；进程重启或超时后恢复待处理事件。同步跳转只展示查询结果，不能触发加积分。
5. 超时订单先查单再关单。关闭过程遇到延迟成功通知，须依据渠道最终结果补账或退款，不能忽略已付订单。
6. 定时查单与每日对账核对实收、退款、到账及异常差额。提供查询、重试和人工处置入口，重试仍经过同一幂等路径。

首期退款由后台审核：按原订单批次核算尚未消费的购买积分，冻结后提交原路退款；成功才完成扣减，失败释放，状态不明继续查单而非提前释放。部分退款、并发消耗和重复通知都必须有独立业务键与累计退款上限；不得用赠送积分兑换现金。

## 6. 原有 quota 迁移

不能把原来以美元展示的额度直接改为人民币或积分。先盘点全部用户、令牌限额、兑换码、赠送余额、已消耗及预扣记录，确认线上扣费参数与批量更新行为。

迁移报告列出每个账户的原始值、原计价依据、来源及建议积分值；来源不明单列待处理。历史购买与赠送按可证明来源分类，不能默认可退款。

历史换算比例须经业务确认后冻结为迁移版本；新充值使用人民币积分规则。迁移使用幂等批次 ID，保留原始值、校验和、前后总量与恢复点。

底层建立单一权威账本，避免积分钱包与旧 quota 各扣一次。执行阶段同步改造请求预扣、最终结算、退款、缓存和并发处理；原 quota 仅作为兼容投影时必须定义唯一写入路径和对账机制。默认 API 响应协议不变。

切换前暂停新订单与新模型请求，排空在途扣费，完整备份后迁移。出问题时先停止新充值／新消费并保全已付款事件，按恢复日志处理；发生新交易后不得直接恢复旧数据库造成付款丢失。

## 7. 实施顺序与交付

| 阶段 | 交付 | 验收 |
|---|---|---|
| P0 纳管 | 网关源码、实际构建版本、部署清单、数据库及恢复方案、全路由清单 | 区分官网与网关部署；完成可恢复备份 |
| P1 品牌 | 品牌配置、全部页面、Logo 衍生资源、旧缓存处理 | 逐页覆盖用户／管理角色、手机、错误和空状态 |
| P2 积分 | 账本、价格版本、预算预扣、任务估算器、迁移工具 | 并发不超扣、不双扣；迁移前后可解释 |
| P3 充值 | 微信／支付宝适配、客户收银台、订单、查单及通知 | 重放、金额篡改、超时、重启均正确处理 |
| P4 后台 | 商户状态、套餐、价格、订单、退款、对账、审计 | 普通客户不能访问；人工操作留痕 |
| P5 上线 | 双渠道小额实付、积分到账、模型调用扣费、原路退款 | 三方账单一致；证明积分能实际使用 |

商户进件与 P1—P4 可同步推进。商户未开通不阻塞文档、界面和模拟通知开发，但必须阻止开启真实收款。

正式开放充值的前提：品牌与价格已发布、商户及支付产品开通、至少一个上游模型真实可用、积分扣费与退款通过验证、恢复方案可执行。

验收必须覆盖：重复回调并发到达、错签名／错金额／错商户、付款后服务崩溃、通知丢失、关单竞态、同一模型请求重复结算、流式中断、缺失 usage、余额不足、退款与消费并发、管理员越权、价格版本切换、旧余额迁移及备份恢复。
