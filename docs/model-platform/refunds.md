# Miraphant 退款账务与支付契约（设计稿）

状态：待业务与技术审核；未实现、未上线、未授权真实退款。  
核对日期：2026-09-27。  
范围：已支付积分订单的原路退款、积分批次冻结/撤销、恢复与审计。本文是下一阶段实现约束，不代表公司已发布退款条款。

## 1. 目标与当前账本

退款必须同时满足两个结果：按原支付通道退回确定金额，并撤销同一笔订单尚未消费的购买积分。两者通过独立退款单和唯一账本操作关联；支付渠道受理不能提前当作退款完成。

现有账本使用整数金额：人民币分 `fen`、微积分 `micro-points`，`1 积分 = 1,000,000 微积分`。当前套餐规则为 `1 元 = 100 积分`，所以套餐快照中 `purchase_micro = amount_fen × 1,000,000`，退款金额每 1 分对应该订单 1 积分。若日后销售折扣、兑换比例或非整数套餐，必须改为读取订单冻结的比例/换算快照，不能继续套用此简式。

每次支付会产生与订单关联的 `purchase` lot；可选赠送独立成为 `bonus` lot。模型消费和退款都必须锁同一 `PointAccount` 与相关 `PointLot`，写入 `PointLedger`，不另建退款余额。当前 `PointLot` 已有 available/held/consumed/refunded 字段，赠送过期也有独立 `expire` 流水；退款目前尚无实体、状态机或渠道接口。

## 2. 可退款金额与积分冻结

### 2.1 默认按原购买批次退未消费积分

默认按积分批次核算，不从账户总余额倒推，也不把赠送、管理员赠送或历史迁移积分兑换成现金。

对原订单 purchase lot：

1. 只允许选择尚在 `available` 且没有被模型请求或其他退款冻结的购买积分。已消费、held、已退款部分不可再退。
2. 在现行比例下，请求退款金额必须为整数分，且对应购买积分恰为 `refund_fen × 1,000,000` 微积分。可退上限为 `floor(可用购买微积分 / 1,000,000)` 分，并同时受原订单金额减去已成功和在途退款金额限制。
3. 创建退款请求时，在一个账本事务中将 purchase lot 可用额转入退款冻结额、账户 `available` 转为 `held`，写入唯一退款冻结流水与精确批次分配。此刻不减少购买 lot 的已入账总额，也不认定已退款。
4. 渠道最终确认成功后，在一个事务内减少退款 hold、增加 purchase lot 已退款额、写退款成功流水并更新退款单终态。失败或审批拒绝才释放冻结；网络未知、通知未到、渠道处理中继续冻结。
5. 退款成功后可退额度永久下降。重复通知、重复查单、同一幂等键重放只能返回同一结果，不能再扣一次批次或账户。

现有 purchase lot 以微积分记已退款值。若按此契约只允许整分退款，必须校验 refund 值是 `1,000,000` 的整数倍；不能使用浮点金额，也不能把截断/四舍五入当成可退额度。

### 2.2 赠送积分撤销是拟议商业规则

当前已批准的套餐方向是首期不赠送。未来若发布带赠送的套餐，以下是建议默认规则，须在开放收款前经业务确认并写入公开退款条款；不能视作客户已经同意：

- 退款只从原支付订单的 purchase lot 退现金，不退赠送积分现金。
- 对该订单的 bonus lot 按累计退款比例撤销：累计目标赠送撤销额 `floor(原 bonus 微积分 × 累计退款购买微积分 ÷ 原 purchase 微积分)`；全额退完时目标强制等于原赠送总额。应冻结的新增赠送额为 `max(0, 累计目标 - 已撤销 - 已自然过期 - 其他在途退款已冻结)`。
- 用累计目标的差额计算，不分别对每个小额退款独立舍入，避免拆单绕过舍入或重复扣赠送。所有乘除用可检查溢出的整数算法。
- 新请求需要的赠送撤销额必须从同一 bonus lot 的未过期、可用余额中冻结。若余额已被消费或用于未决模型 hold，暂不批准该退款额；可降低退款申请金额重新计算。不得扣其他赠送、购买批次或产生负余额。
- 已自然到期的赠送已失去可用价值，不为其收现金，也不再重复撤销。到期流水必须与退款撤销流水区分统计。已经自然到期的部分计入累计赠送抵扣，但不能增加可退款购买分。
- 退款冻结期间 bonus 到期：退款成功时按已批准退款关系记为退款撤销；审批拒绝或渠道明确失败时释放仍 held 的积分，但按原过期时间处理，已过期部分进入 `bonus_expired`（或等价独立过期流水），不能复活成可用余额。状态未知期间不释放，待最终证据后再分别执行。

赠送计算示例：支付 ¥10（1000 分），购买 1000 积分、赠送 200 积分。先退 ¥1（100 分），撤销 100 购买积分并冻结/撤销 20 赠送积分；再退 ¥1 时累计目标为撤销 40 赠送积分，第二次只再冻结 20。若 bonus 在两次退款之间自然到期，未撤销且已过期余额作为过期处理，不再向第二次退款重复扣赠送。若用户已消费 190 赠送积分、可用只剩 10，申请退 ¥1 需再撤销 20 赠送积分，则本次不能按 ¥1 批准；可申请最多 ¥0.50（对应购买 50 积分并撤销 10 赠送积分），或者等待相关 hold 结算后重新核算。额度冻结时已 held 的赠送不可被退款重复占用。

微积分舍入示例：原订单支付 ¥0.03，购买 3 积分、赠送 10 微积分。累计退 ¥0.01 时目标为撤销 3 微积分；累计退 ¥0.02 时目标为 6 微积分；累计退完 ¥0.03 时目标为 10 微积分。每次只追加目标差值，最终不会剩下因逐笔舍入而未撤销的赠送。

### 2.3 同一原单顺序退款

建议同一原支付订单同一时刻最多存在一笔非终态退款，包括待审核、待提交、处理中、未知和待人工核查。通过订单行上的活动退款指针或唯一退款占用行，在事务中原子取得该占用；该退款进入成功、最终失败或审核拒绝等终态后释放占用，才允许创建下一笔部分退款。这样前序审批/渠道结果未决时不会让后续请求基于旧累计金额和旧赠送撤销快照并发审批。

退款成功后可以顺序申请下一笔；每次重新读取渠道已确认累计额和账本成功/过期/在途赠送数。长期 `unknown` 或 `needs_manual_review` 会阻止同单后续退款，直至有证据处理完成；不能用超时自动清掉占用。

### 2.4 与模型请求并发

- 退款请求与 `Reserve`、hold settle/release、注册/赠送、支付到账和过期清理必须使用一个跨所有写路径的锁序与事务策略。事务先按同一规则锁定账户、预算/业务单、批次，再过期清理和重算可退额；任何一方抢到积分后，另一方依据新余额失败或接受更小金额，不允许透支或重复占用。
- 已存在的模型 hold 不可直接退。若模型请求为 `held/pending/needs_review`，其资金不属于退款可用额；未知 usage 必须先按现有待核实流程裁决。
- 退款 hold 建议有单独 `PointRefundAllocation`，但与账户/lot 的 held 汇总共享同一余额。每一分冻结都有退款 ID 与 lot ID，可查、可回放；消费 hold 与退款 hold 不可仅凭账户总 held 互相释放。
- 禁止在数据库事务内进行支付网络 I/O。先事务冻结并记录稳定退款号，再调渠道；使用新事务写响应证据/状态。进程崩溃或客户端取消均不得释放冻结。

现有写路径尚未统一锁顺序：例如 `Reserve` 先处理过期 lot 再更新账户/lot，到账处理先锁订单再创建 lot、更新账户。因此，退款实现前必须先定并改造共享账本写入口，不能只在退款函数中加 `SELECT ... FOR UPDATE` 就宣称跨路径安全。建议锁序为：先通过 user ID 取得/创建并锁 `PointAccount`；再按稳定类型顺序锁 token budget、订单/hold/refund 业务行；最后按 lot ID 升序锁所有相关 lot。涉及 hold/refund 但还不知道 user ID 时，可先无锁读取其不可变 user ID，再锁账户并重新读取/锁业务行确认。清理到期额度也遵循账户在先、lot 在后。该顺序需同步覆盖 reserve、settle、release、credit、grant、expiry 与 refund。

SQLite 必须在首个读之前取得可序列化写事务（例如经验证的 immediate transaction/账户互斥行），使用有限 BUSY 重试；业务重试不包网络副作用，commit 结果不明按业务键回查。若后续 MySQL/Postgres 不能证明相同序列化不变量及行锁顺序，退款能力只对已验收 SQLite 单实例开放，其他数据库明确 503，不能声称通用并发安全。

## 3. 退款数据与状态

退款需新增独立数据契约，不能复用充值 `PaymentEvent` 或客户支付订单状态。建议最小模型：

| 实体 | 关键字段/约束 |
|---|---|
| `point_refunds` | 内部 refund ID、唯一 `refund_key`、客户/原订单 ID、渠道、冻结的 merchant/app/支付交易身份、退款分(整数)、购买微积分、赠送撤销微积分、币种、状态、客户原因摘要、审核人/时间/决定原因、渠道退款单号、渠道退款交易号、提交/最终确认时间、有限脱敏错误码；申请快照和审核结果不可变追加 |
| `point_refund_allocations` | refund ID、lot ID、lot kind、购买退款微积分/赠送撤销微积分、冻结/完成金额；唯一关系防一份批次重复分配 |
| `point_refund_events` | 渠道/稳定事件键唯一、refund ID、通知摘要 digest、规范化状态/金额/身份、验签结果和处理状态；不得保存原始签名、密钥、完整通知或买家资料 |
| `point_ledger` | append-only：退款冻结、退款完成、失败/拒绝释放、赠送撤销、赠送自然过期分别用清晰 `kind` 与唯一业务键；关联 refund ID、原订单、lot 和用户 |
| `point_admin_audit` | 单独记录申请审核、批准/拒绝、发送/重试、查询恢复、异常裁决；actor/业务键/原因有唯一性和不可变保护 |

金额快照锁定原支付订单的 CNY 金额、渠道、merchant/app、provider transaction ID、下单金额、套餐版本、purchase/bonus 数、有效期和累计已退金额。旧订单缺 merchant/app/交易号等身份快照时，不得从当前配置补填；转人工核查，不自动调用退款。

建议状态：

`requested → reserved → awaiting_review → rejected`  
`requested → reserved → approved → submitting → submitted → succeeded`  
`submitting → unknown → (同号查单/安全重试) → submitted | succeeded | definite_failed | needs_manual_review`  
`submitted → definite_failed | succeeded | needs_manual_review`

其中：

- `requested/reserved` 必须同一数据库事务提交，或全部回滚。
- `approved` 和 `rejected` 是互斥、追加审计的授权决定；拒绝释放冻结。
- `submitting` 在任何外部网络请求前持久化。请求超时、进程崩溃、响应无法验真均转 `unknown`，资金保持冻结。
- `submitted` 仅代表渠道受理，继续保持冻结。
- `succeeded` 只能由已验真的最终通知，或已验签查单的协议可用字段完全匹配的成功终态触发。商户/App 身份从冻结的订单与配置实例、发出的签名请求及应答验签上下文绑定；只有渠道协议实际返回的 merchant/app 字段才逐字段比较，不能要求不存在的字段。
- `definite_failed` 只用于可证明未发生退款或渠道最终关闭的状态。未知、暂时查不到、网络失败、处理中不能作为失败。
- `needs_manual_review` 用于身份冲突、金额冲突、微信 `ABNORMAL`、账本/渠道无法确定一致等问题；冻结留存，不能提供跳过验签的“直接补钱/退款成功”操作。

一次部分退款对应一个不可变 refund request 和一个渠道退款号。修改金额、订单、商户、币种或付款交易身份都必须创建新的、可审核的退款申请；同一个渠道退款号不能换金额。审核拒绝/最终失败释放后若再次发起，使用新的内部申请幂等键。支付宝在相同请求号和金额下重试；微信仅在查询确认前单请求尚不确定时原号重试，查询确认 `CLOSED` 后若平台允许重新申请，必须经过明确的新审批并生成新 `out_refund_no`，不能自动翻新。

## 4. 原路退款协议约束

网络调用必须始终使用退款记录冻结的 provider/merchant/app 和原支付交易 ID；不允许使用用户提交的渠道、交易号、金额或 URL。只支持原路退回。凭据来自服务器配置，日志/DTO 只给脱敏状态。

### 微信支付 API v3（Native 首批）

- 退款申请使用固定官方 endpoint `POST /v3/refund/domestic/refunds`。商户退款单号 `out_refund_no` 最多 64 字节；同号多次申请只退款一笔。原因字段最多 80 字节，中文按 UTF-8 字节限长，不能按字符数截断。
- **申请调用**由原支付订单和冻结配置生成 `out_trade_no` 或 `transaction_id`、`out_refund_no`、`amount.total/refund/currency`；请求 Authorization 使用绑定的 merchant credentials。微信的退款申请/查询响应未提供 `mchid`/`appid` 字段，不能要求响应包含它们。仅接受由对应微信公钥/平台证书验证过的应答；协议要求的退款号、原单号/交易号、状态和金额等字段若缺失就拒绝，不得凭空补值。协议本身不提供的 merchant/app 身份通过签名请求的冻结配置上下文绑定。
- **查单调用**按稳定 `out_refund_no` 查询，商户身份来自该退款记录冻结的配置实例与签名请求上下文，回包验签使用同一配置。当前 Native 查询响应结构含 `refund_id`、`out_refund_no`、`transaction_id`、`out_trade_no`、`status`、`amount` 等，没有 `mchid`/`appid`；所有协议要求字段必须存在并与本地 refund/order 快照匹配，对商户/应用身份不从响应捏造字段。
- **结果通知**先验外层微信签名并 AES-GCM 解密。退款 resource 明确提供 `mchid`、`out_trade_no`、`transaction_id`、`out_refund_no`、`refund_id`、`refund_status` 和 `amount.total/refund/payer_total/payer_refund`；比对 `mchid` 与冻结 merchant，其他字段与退款单和原支付订单一致。该通知结构没有 `appid`，app identity 通过原订单冻结的 `app_id` 与本地该商户配置关系约束，不要求通知缺席字段。
- 请求参数使用原单 `out_trade_no` 或 `transaction_id`、原单总金额 `amount.total`、本次退款整数分 `amount.refund` 和 `CNY`。每次申请退款不超原支付金额；多笔累计退款不超原单。
- 商户文档要求单笔退款最多 50 次部分退款；同一订单后续部分退款需更换退款单号并间隔至少 1 分钟。申请失败重试用原单号和原参数，避免重复退款。官方接口明确 2xx 申请成功仅是“已受理”，不能作为完成凭证。
- 最终退款状态取 `SUCCESS`、`CLOSED`、`PROCESSING`、`ABNORMAL`。只有 `SUCCESS` 可完成积分扣减；`PROCESSING` 保持冻结；`CLOSED` 是渠道终止状态，可按失败释放并需单独审批是否创建新退款单；`ABNORMAL` 表示原路退款异常，转人工，不得假定退成或直接释放。
- 退款结果通知先验证微信签名头和原始 body，再用 APIv3 密钥 AES-256-GCM 解密 resource；验真后才持久化规范化 inbox。通知需核对商户/原订单/原交易/退款号和金额。回调仅在 durable event 已写入后确认。按官方推荐查询退单号，开始约每分钟一次，5 分钟仍处理中后退避；限流或网络故障不改变退款终态。
- 微信退款申请有效窗口按当前 Native 文档为付款成功后 365 天。实际场景/商户合同若更严格，按较早截止时间拒绝新的退款申请并提示人工联系。渠道退款资金到账可能延迟，按最终状态处理。

### 支付宝

- 使用固定已签约的 `alipay.trade.refund` 与 `alipay.trade.fastpay.refund.query`，必须带签名、验签响应，不接受客户端拼出的网关 URL。
- `out_request_no` 是此笔退款稳定请求号；每个部分退款请求号不同。相同订单不同退款至少间隔 3 秒。请求超时/不确定时先用相同订单与 `out_request_no` 查询；若重试，退款号与金额保持一致。
- **提交调用/响应：**请求的 `app_id`、`out_trade_no`、`trade_no`、`out_request_no` 和本次退款金额来自冻结的服务端配置、原订单和退款单；响应必须验签。退款接口响应有 `trade_no`、`out_trade_no`、累计 `refund_fee` 和 `fund_change`，但不能假设它返回 `out_request_no`。`code=10000` 仅代表调用成功；`fund_change=Y` 可表示发生资金变化，但必须核对原单及退款金额/累计金额；`fund_change=N` 或缺失继续查询。
- **查单调用/响应：**请求以稳定 `out_request_no`、原订单身份查询。官方退款查询响应有 `trade_no`、`out_trade_no`、`out_request_no`、原单 `total_amount`、本次 `refund_amount` 和 `refund_status`；该查询响应没有 `refund_fee`，所以不把它列为查单必填。匹配原订单号、交易号、请求号、总金额和本次退款金额；应用身份来自发起请求的冻结 app 配置及验签上下文，不要求响应中不存在的 app_id。查询 `refund_status=REFUND_SUCCESS` 才明确成功；查询至少间隔 10 秒，过早查询可能尚未显示后续成功，缺状态不得释放。
- **累计金额陷阱：**退款提交响应的 `refund_fee` 是原交易累计已成功退款金额，不是本次申请金额。若 `fund_change=Y` 且响应带此值，核对为本次成功前已确认累计额加本次金额；不匹配即隔离，不按其差值自动改本地金额。退款查询响应没有 `refund_fee`，只以其返回的该退款请求 `refund_amount` 验证本次请求；总上限用本地唯一成功退款记录与在途预留金额约束。金额使用十进制字符串严格转整数分，拒绝浮点/科学计数/多于两位小数/溢出。
- 商户级可退款期限取签约产品规则。支付宝文档说明超过签约可退款时间的原单不能退款；创建前查询当前配置的期限，未知时不自动提交。

以上协议来源为支付平台当前公开商户文档；实施前应再次核对商户实际签约产品和 API 版本。产品开通未完成时只允许合成签名、隔离 endpoint 的协议验收。

## 5. API、页面、权限与审计

### 客户入口

- `POST /api/payments/orders/:id/refund-requests`：从当前 session 确定用户，只接受金额分、理由、稳定客户端幂等键；金额不可超过服务端计算的可退额度。CSRF、用户级限流、订单归属及重复键完整参数检查必须执行。返回申请状态、冻结积分、可读原因和下一步，不暴露渠道密钥/签名/原始通知。
- `GET /api/payments/orders/:id/refunds`：本人订单退款记录与已脱敏进度；始终用当前 user ID 加 order key 查询。不能因为猜到 ID 查询他人订单。
- `/console/orders/:id` 提供退款申请按钮、分金额、购买积分冻结量、赠送撤销说明、是否需要人工审核、状态和更新时间；订单有处理中请求时禁用重提。客户不能选择退款到账账号/新渠道。
- 钱包按订单/购买批次展示购买积分余额及“可申请退款”的估算，必须标注最终以服务端锁定时核算为准；不能把积分钱包总额直接称可退款现金。

### 管理入口

- `/admin/refunds`：财务/管理员查看退款申请、原单支付快照、可退购买批次、赠送撤销分配、审核记录、脱敏渠道状态、待核实队列和恢复操作。
- 建议 API：`GET /api/admin/payments/refunds` 分页筛选；`GET /api/admin/payments/refunds/:id` 只读详情；`POST /api/admin/payments/refunds/:id/approve`、`reject`、`submit`、`reconcile` 均 CSRF 且使用业务幂等键。原路提交/查单网络调用在 DB 事务外。
- 只允许显式的 provider adapter 提交原路退款。不得提供“直接标成功”“直接减少余额”“绕过 provider”的人工按钮；有证据的账务纠正走单独、不可变、双人审批调整流程，另行设计。
- 每个申请、批准/拒绝、提交、查单、恢复、人工裁决都写 append-only 审计：actor、目标用户/订单、金额分、购买/赠送微积分、请求业务键、旧/新状态、reason、时间和脱敏结果。渠道交易 ID 与通知 ID 对客户隐藏；审计通过内部 refund/order ID 精确关联。

### 身份与高风险认证

当前可用的服务端身份模型只有现有客户及管理员权限；规格中拟议的 `finance` 和客服只读角色尚未完成。本阶段不能把普通管理员 UI 显示当权限。退款上线前至少：

1. 现有角色值为 1/10/100，points session auth 的 `minRole` 是数值阈值。不要给 finance/support 分配 10 与 100 之间的数值并复用 `minRole`，否则会继承所有阈值以下/以上旧管理权限。应建立独立的 capability → route/action 映射，例如 `refund.read`、`refund.review`、`refund.submit`、`refund.reconcile`；授权按最新 DB 用户状态和明确 capability 检查，撤权立即生效。一个通用 `admin` 页面可见性判断不能替代每个 action 的授权。
2. 退款审核与最终提交建议双人职责分离（申请/审核/提交至少两名不同操作者，配置小额例外也需明确阈值和审计）。
3. 高风险批准/提交必须有短期重新认证，并将服务端签发的一次性票据绑定到 `actor_user_id + refund_id + action + amount_fen + expires_at`；票据使用后失效，重放/更改金额/更换退款 ID 均拒绝。普通登录 cookie 和 CSRF token 只证明会话/请求来源，不是二次认证。当前若无可用 MFA/step-up，不得悄悄以普通 session 替代，需在正式开放门禁中阻断。
4. 财务与客服 DTO 不得输出商户证书、私钥、APIv3 密钥、客户访问密钥或完整通知签名。

## 6. 幂等、恢复与一致性

- 客户幂等范围为 `user + order + client_idempotency_key`，同键必须比较完整金额/理由/订单。参数相同返回原申请，冲突返回 409，不另冻结或提交。
- 渠道幂等键由服务端在审批冻结后生成并持久化，绑定 provider、商户/app、原交易、退款金额、币种、refund ID。唯一索引保证同一渠道号不能跨退款/原单复用。所有重试先查询该号；未知时不换号、不换金额、不创建替代订单。
- 先冻结并写 `submitting`，然后网络调用；任何外部 HTTP 在事务外。网络超时/进程崩溃期间保留冻结，启动恢复扫描 `submitting/unknown/submitted`。完成每个项目需有扫描上限、游标和 attempted/succeeded/failed/skipped 报告，不能让一个坏配置挡住其他渠道。
- 渠道成功事件先验签/校验，持久化唯一 inbox 后再确认。处理事务按 2.4 定义的统一锁序，核实当前状态、通知 ID、退款交易 ID、协议实际提供的商户身份字段、金额和累计上限，再原子写退款 ledger、lot/account 状态、refund `succeeded` 与 event `processed`。
- 相同成功通知重放、不同通知 ID 但同一渠道退款交易重复、通知和查单竞速，最终都只能有一个退款 credit/debit 结果。对同一渠道 refund ID 的唯一归属应由独立交易/退款 owner 约束保护，不能仅靠 inbox event ID。
- 数据库 commit 报错时用退款业务键和 inbox 状态回查是否已提交；不得在未知事务结果后再发新渠道退款。
- 退款开始后更换商户配置不影响老退款：始终用订单冻结的 merchant/app 和该配置版本处理。缺历史身份快照或配置不可用时挂起人工核查，不能发往新商户。

## 7. 失败矩阵

| 事件/结果 | 退款状态 | 资金处理 | 恢复动作 |
|---|---|---|---|
| 参数/归属/可退额校验失败 | 未创建或 `rejected` | 不冻结；如已预冻结则事务回滚/释放 | 客户修正后用新请求键 |
| 申请后财务拒绝 | `rejected` | 释放冻结；赠送按原期限，已过期则记自然过期，不复活 | 保留审核审计 |
| provider 调用前本地确定失败 | `definite_failed` | 安全释放冻结 | 记录本地错误码 |
| 网络超时、进程退出、验签失败、响应无法解析 | `unknown` | **继续冻结** | 对同一退款号查单；修复配置后续扫 |
| 微信 HTTP 受理/支付宝 `code=10000` 但状态非最终成功 | `submitted` | **继续冻结** | 按供应商频率查状态或等通知 |
| 渠道最终 success，身份和金额匹配 | `succeeded` | 扣掉退款 hold、purchase lot 记 refunded、赠送按规则撤销 | 同一事务完成；重复事件幂等 |
| 渠道最终明确失败/CLOSED，所有身份已匹配 | `definite_failed` | 释放未过期部分；过期 gift 记 expire | 若重试，遵循该渠道原号/新号规则并重新审批 |
| 微信 `ABNORMAL`、商户/订单/金额/currency/累计额不匹配 | `needs_manual_review` | **继续冻结** | 对账与渠道商户后台核实；不自动补账 |
| 重复/冲突渠道 refund ID 或同一原单累计超额 | `needs_manual_review` | **继续冻结** | durable quarantine、告警及人工裁决 |
| SQLite BUSY/事务冲突 | 事务回滚；请求可重试 | 不发生外部 I/O；若是否提交不明则业务键回查 | 有界代码重试只包数据库事务 |
| 渠道明确成功但 DB 短暂不可写 | 通知先持久化；保持待处理 | 暂不完成积分扣减/冻结保留 | 恢复 worker 从 inbox 重放；渠道回调先 durable 后 ACK |

没有“TTL 到期自动解冻”。退款最终结果可能晚于本地 timeout；只可基于渠道明确最终状态或有完整证据的人工决策释放。人工裁决必须记录依据和操作者，不能通过改写 append-only 证据实现。

## 8. 定向验收计划（实现阶段门）

以下需先用临时 SQLite、合成客户/管理员、合成密钥和隔离 `httptest` provider 验证；所有写操作仅访问本地测试 endpoint，不调用真实商户，也不运行生产退款。

1. **整数与上限**：¥10 套餐；累计分级退款；1分/微积分边界、溢出、金额小数非法、累计退款等于/超过原单金额；已消费与已退款购买积分不计入上限。
2. **bonus 数值**：前述 1000 purchase/200 bonus 部分退两次，验证累计舍入；gift 已消费、过期、held、退款冻结期间到期，逐项检查 expire 与 revoke ledger/account 后状态不重复入账。
3. **并发**：refund reserve 与模型 Reserve/Settle/Release 同步 barrier 竞争，余额不透支、lot/账户 held 总数一致、两个 refund 不能冻结同一积分；DB 多连接 SQLite 的安全回滚/冲突回查覆盖。
4. **审批与权限**：普通用户仅创建本人订单申请；他人订单 404、无 CSRF 403、撤销财务角色后旧 session 403；未二次认证不能审批/提交高风险退款；客户、客服不能提交 provider 请求。
5. **渠道协议**：微信 RSA 响应验签/通知签名+AES-GCM 解密，Alipay RSA2 请求与原始响应验签；伪签名、错 merchant/app、错原单/交易、退款单号、币种、金额、累计额分别隔离且不改账。
6. **状态与重放**：提交成功但 response 丢失、通知先于 API response、重复通知/不同 event ID 同 refund ID、查询与通知竞速、CLOSED/ABNORMAL/PROCESSING、支付宝查询缺 `refund_status`、提交响应 `refund_fee` 累计陷阱、provider 429/500、进程重启恢复；不确定永远保持冻结。
7. **生命周期**：部分 refund A 成功再申请 B；A 失败重试同键同金额；退款完成后的余额与每个 lot/ledger 可解释；禁止重复到账/超原交易累积。
8. **UI/运营**：客户订单与后台退款列表在 390px/桌面覆盖 loading/empty/error/403/unknown/success；未知状态不会显示成功/失败；后台可按游标恢复所有记录，渠道原始凭据不出现在 HTML、日志、审计 DTO。
9. **真实付款门禁**：上线前在签约 sandbox/受控小额实付完成双渠道原路退款端到端验收，核对商户账单与本地退款额/积分批次；测试报告包含服务二进制 SHA、配置版本、provider 交易和回滚/恢复证据。不满足商户/模型渠道/积分计费/MFA/角色门槛时保持退款入口关闭。
